# ADR-003: The newsletter plugin

| Field      | Value                                                                                         |
| ---------- | --------------------------------------------------------------------------------------------- |
| Status     | Proposed. Accepted when the M5 pull request lands (its `astro.config.mjs` change is PATH_ASK). |
| Date       | 2026-11-23                                                                                    |

## Context

An Admin builds a quarterly newsletter with one section per body, previews it in a real inbox, and sends it to subscribers through a Resend Broadcast (spec FR-6). Visitors subscribe from the site (FR-7). EmDash's system email goes through Resend too (FR-8.1). The constitution adds four rules: the Resend SDK never reaches the browser, TipTap JSON is the editable source and the composed HTML the send artifact, nothing reaches subscribers without a test send and an Admin's approval, and every send carries an unsubscribe link.

Three facts found in M5 shape the design:

1. `resend` 6.39's `broadcasts.create` takes no idempotency key (R3, receipts). A retried request could create a second Broadcast.
2. `composeReactEmail` needs a TipTap `Editor`. The server could build one headlessly, but `@tiptap/core` is not a direct dependency, and adding it changes how pnpm resolves EmDash admin's pinned TipTap peers.
3. A Broadcast's event list goes stale between assembly and approval (R13).

## Decision

```
admin page (browser)                plugin routes (Worker)                     Resend
EmailEditor ── save: JSON + HTML ──▶ issues/save      store, revision + 1
            ── test ───────────────▶ issues/test-send  footer, allowlist only ──▶ emails.send
            ── approve ────────────▶ issues/approve   step(approve), refresh events,
                                                       hold (compare-and-set) ──▶ find by key, else
                                                                                   broadcasts.create
visitor form ── POST ─────────────▶ subscribe        Origin, zod, Turnstile ──▶ contact upsert
archive pages ─ GET, in-process ──▶ archive/list     sent issues only
                                    archive/issue
EmDash email ───────────────────────▶ email:deliver   cc, replyTo ─────────────▶ emails.send
```

- **Domain in core, I/O at the edges.** The lifecycle (`step`), assembly, the event refresh, the footer and the archive transform are pure functions in `src/lib/core/newsletter`. `src/plugins/newsletter/service.ts` orchestrates them over three ports: the issue store, the mailer and the clock. Routes parse input (zod) and map errors to HTTP. `src/lib/adapters/resend-mailer.ts` is the only module that imports `resend`, and lint lets only the plugin's server modules import it.
- **Compose in the browser, send from the server.** The admin page saves the editor's `getJSON()` and `composeReactEmail({ editor, pretty: false })` together, so each revision's HTML comes from the same editor state as its JSON. The server adds the unsubscribe footer itself (`withFooter`), so a send has the link whatever the document holds. Approve sends the stored HTML of the revision that was test-sent, so subscribers get what was previewed. This departs from FR-6.4's wording, which has the route compose; the alternative was a new TipTap dependency that moves EmDash admin's editor onto another TipTap version.
- **Approval is idempotent.** Approve runs `step(issue, approve)` (FR-6.6 refuses an issue not test-sent at its current revision), then writes the issue as `creating` with a short hold, by compare-and-set on the storage row. Of two concurrent approvals only one write applies. The holder looks the Broadcast up by its name, the key `fm-issue:<id>:rev:<n>` (FR-6.7), before creating one, and records the Broadcast id. A retry finds `creating`: while the hold lasts it is refused; once the holder has finished, failed or crashed it takes the hold and repeats the lookup, so a crash between Resend and the store never sends twice. A definite refusal from Resend returns the issue to a tested draft. An unknown outcome keeps it `creating` and frees the hold.
- **Events are re-read at approval (R13).** If any body's event list changed since assembly, approval updates it, counts that as an edit, and asks for a new test send.
- **Archive in a sandboxed frame (FR-6.8).** The stored email is a whole HTML document, so `/newsletters/[slug]` shows it in an `<iframe srcdoc sandbox="allow-popups allow-popups-to-escape-sandbox">`: no scripts and no same-origin access, and links open in a new tab. Nothing is spliced into the page, so the `set:html` ban holds. The per-recipient unsubscribe footer is swapped for a signup link.
- **The archive pages read through public plugin routes.** For an anonymous visitor, EmDash's middleware gives a public page a reduced `locals.emdash` with no `db` (the `isAnonymousPublicPage` branch of `emdash/dist/astro/middleware.mjs`). What it does give every page, signed in or not, is `handlePublicPluginApiRoute`, which `emdash/plugin-utils` exports as `getPublicPluginApiRouteHandler`, documented there as "the public-only plugin route dispatcher exposed to SSR page components". It dispatches only routes declared `public: true`. So the plugin declares two read-only `GET` routes, `archive/list` (slug, subject, date of each sent issue) and `archive/issue?slug=` (the same plus the sent HTML), and the pages call them in-process. Drafts, revisions, Broadcast ids and the TipTap source never leave the plugin. A failed read throws rather than rendering an empty archive, because an empty archive must mean nothing was sent. Rejected: building a `PluginStorageRepository` from `emdash/request-context`'s database handle, which reaches past the plugin into its storage from page code with no documented contract.
- **Plugin routes are classified.** ADR-002's route table passes every plugin route to EmDash, which checks the route's permission. `PLUGIN_ROUTES` in `route-table.ts` records each newsletter route's guard (`settings:manage`, which only Admins hold, or a public route's own checks: the signup form's, and the archive's read-only `GET`s), and a unit test fails when a declared route is missing or differs.
- **Signup is a plain form post** to a public plugin route answered with a 303 back to the form. EmDash's middleware already refuses a cross-origin post to a plugin route; the route checks again and also refuses a post with no Origin unless it carries `X-EmDash-Request: 1` (FR-7.2). A new contact is created in the subscribers Segment with the newsletter Topic and each ticked body's Topic. Anyone can type anyone's address, so the public form never reverses a choice an existing contact made (M7 review M1): when Resend reports the contact as `unsubscribed`, or opted out of the newsletter Topic, nothing is changed and the form says the address unsubscribed before and how to opt back in (the preferences link in a past newsletter, or the Temple). Otherwise the contact is added to the Segment and opted in to the ticked Topics it has not opted out of; its Topic list is read first, and if it cannot be read nothing is changed. An existing subscriber who once opted out of a body adds it back from the preferences link, not the form.
- **Outside production, nothing reaches an address off the allowlist** (constitution § Newsletter and email; M4 verification N1, M7 review B1). `gateOutbound` (`src/lib/adapters/send-gate.ts`) wraps the real Resend mailer unless `SITE_ENV` is exactly `production`. It refuses a single email with any recipient off `NEWSLETTER_TEST_ALLOWLIST` and `@resend.dev`; a signup for such an address, before Resend hears of it, so the visitor reads that this is a test copy of the site (`test-site`); and the creation or sending of a Broadcast unless every contact in its Segment is on the list. The Segment is listed through the mailer port at that moment, every page of it, and a Segment or Broadcast that cannot be read refuses. A refusal is a `blocked` mailer error: the approval says why, and the issue stays a tested draft. Resend applies a Segment when it sends, so a contact added to the staging Segment in the dashboard after a Broadcast was scheduled is not checked; the signup gate keeps the site from adding one.
- **Every recipient is one address** (M7 review L4). `parseAddress` (`src/lib/core/address.ts`) accepts one bare address and nothing that separates, quotes or names another. The gate counts any other recipient as off the list, so `"victim@example.com,delivered@resend.dev"` cannot pass as a Resend test inbox, and a body's contact recipients and the allowlist drop such rows.
- **Forms trust only their own Turnstile tokens** (M7 review L7). Each widget names its form in `data-action` (`subscribe`, `contact`); siteverify must answer that action and a hostname of the form's origins, so a token solved on another site with the same widget, or in the other form, is refused.
- **Form counters expire by sweep** (M7 review L5). Plugin KV has no expiry, and a config plugin's `cron` schedule would be registered only by `plugin:activate`, which EmDash runs once per database, so it would never reach a database that already has the plugin. The first request in a target's new window deletes the form's counters from earlier windows instead, twenty at most a sweep.
- **No address in a console line** (M7 review L2). EmDash's `email:deliver` contract reports a failed delivery only by a throw, and EmDash then logs the recipient's address; a transport that returned instead would make a refused invite read "Invite sent". So the Worker wraps the console at start-up and replaces every address in string and error arguments with `[email]` (`redactConsoleEmails`), for EmDash's lines as for ours.
- **Settings are read at runtime.** `RESEND_FROM`, `RESEND_SEGMENT_ID`, `RESEND_NEWSLETTER_TOPIC_ID` and `NEWSLETTER_TEST_ALLOWLIST` are not secrets, but they are `astro:env` fields with `access: "secret"`, because that is how `astro:env` reads a value from the Worker's env (`cloudflare:workers`) at runtime; a `public` server field is inlined by the build. Each environment sets them in its `vars` in `wrangler.jsonc`. `tests/build/check-runtime-env.mjs` builds with a sentinel in each and fails if one reaches the bundle. `TURNSTILE_SITE_KEY` was a client field, inlined by the build; since M4 it is read the same way, because only server-rendered forms use it.
- **Fakes only under `astro dev`.** Without keys, or with `RESEND_FAKE`, the dev server uses an in-memory Resend and an offline Turnstile check. `chooseProvider` returns a fake only when `import.meta.env.DEV` is true, and the fake module is imported only inside that branch, so builds do not contain it. Two Admin routes exist only on the dev server: `dev/outbox` shows what the fake received, and `dev/unsubscribe` records a global unsubscribe as Resend would. `tests/build/check-dist.mjs` fails CI if a build contains the fake or either route, and scans source maps too.

## Consequences

- An Admin must save before a test send or approval; the page disables both while there are unsaved changes.
- The stored HTML is what the Admin's browser composed. An Admin could store HTML that does not match the JSON through the API. Admins are trusted (Q5), the footer is added on the server, and the archive frame runs no script.
- Only one issue is open at a time: "New issue" returns the open draft, and a draft can be discarded to start again.
- The newsletter plugin registers EmDash's `email:deliver` transport only when it can send: `RESEND_API_KEY` and `RESEND_FROM` set, or the dev server's fake. Until then EmDash keeps showing invite links for an Admin to share. On the dev server, system email lands in the fake outbox instead of EmDash's dev console.
- That choice is made when EmDash builds its plugins, and on Workers the Worker's secrets are bound by then. EmDash's generated `virtual:emdash/plugins` module calls each `createPlugin()` lazily, from runtime initialisation during the first request of an isolate, and `@astrojs/cloudflare` points `astro:env` at the `cloudflare:workers` env when its handler module loads, before any request. Checked on the production build under `wrangler dev` with a dummy `RESEND_API_KEY` in `.dev.vars` and `RESEND_FROM` set: a temporary log showed `createPlugin` called from `plugins < getPlugins < buildDependencies < initWithLock` with the transport registered; without the key it was not. Changing a secret deploys a new Worker version, so an isolate never holds a stale choice.
- Two behaviors need the staging send test: whether Resend honours `Idempotency-Key` on broadcasts (the key-named lookup does not depend on it), and how the contact endpoints answer for an existing contact (STATUS).

## Accepted residual risks

Recorded in the M7 review fixes (TASK.md § M7 review fixes) for the lodge's sign-off with ADR-002's list (PLAN Q14).

1. **The staging Segment is checked when a Broadcast is created, not when Resend sends it.** A contact someone adds to the staging Segment in the Resend dashboard after a Broadcast was scheduled receives it. The site itself cannot add one: the signup gate refuses every address off the allowlist outside production.
2. **Rotating networks inside a /48.** The form limits count an IPv6 /64 as one network, so a sender holding a /48 has 65,536 of them. Each signup still needs a Turnstile pass, and the per-target caps (sixty signups an hour in all, thirty messages an hour per body) bound the volume; the cost is one counter row per network per window, which the sweeps delete twenty at a time.
3. **Addresses the console redaction cannot see.** An address inside an object passed to the console whole, or in a URL path, reaches Workers Logs as it is; no EmDash line seen does either. Span attributes other than URLs were not inspected on real traces. Workers Logs keeps 7 days (`docs/observability/workers-logs.md`).
4. **Scheduled publishing is watched from inside the Worker only.** Once an hour the Worker checks that no collection holds an entry the run had to publish and did not (TS.1), and logs `scheduler.overdue` at error level, which Workers Issues turns into an alert. The run's other steps (plugin cron, cleanup, cache purges) log plain-text lines that only the saved queries show (`docs/observability/workers-logs.md`). A backlog of more than 100 due entries in one collection, which EmDash drains 100 a minute, is reported until it has drained. Since the Checkly heartbeat was removed (2026-11-27, Cloudflare-only monitoring), a cron that stops firing altogether raises no alert: nothing runs to log anything. The Worker's Metrics tab shows the cron's invocations.
5. **A failed purge leaves a page stale until its max-age.** An hour at most for content pages, fifteen minutes for what comes next, five for the archive; the failure is logged (`cache.purge_failed`). After a rollback, the earlier version may serve its own copies, an hour old at most, and nothing but another deploy clears a Worker's cache.
6. **A hand-typed slug with a percent escape is unreachable.** Astro decodes a path until it stops changing before routing, so a slug like `50%41` arrives as `50A`. EmDash's slugify never writes `%`; a bare `%` (`pct%zz`) works.
7. **A subscriber cannot re-add a body they left from the form.** The form never reverses an opt-out, so someone who opted out of a body's Topic and ticks it again stays out; they use the preferences link in a past newsletter.
8. **Maybe: an existing subscriber cannot add any body from the form.** Body Topics default to "opt out". Resend's contact-topics answer (`ContactTopic` in resend 6.39) carries only `subscription: "opt_in" | "opt_out"`, nothing that tells a default from a contact's choice, so if Resend lists a Topic the contact never chose as `opt_out`, risk 7 covers every body Topic of every existing contact. Not knowable from the SDK; deploy.md § Check step 6 settles it on staging before launch. Recorded in the second round of review fixes (TS.5).

## Alternatives considered

- **Compose on the server with a headless TipTap editor.** Measured to work in Node, but needs `@tiptap/core` as a direct dependency, which re-resolves EmDash admin's TipTap peers. Revisit when EmDash and the editor share a TipTap version.
- **Rely on an idempotency header alone.** Not offered by the SDK for broadcasts and undocumented for the endpoint.
- **`set:html` or a raw `.html` route for the archive.** The first breaks the constitution's rule. The second is safe with a sandbox CSP, but a plugin's raw responses cannot be `text/html`, so it would be a page route; the iframe is one request and one file.
